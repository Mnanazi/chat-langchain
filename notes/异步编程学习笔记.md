# 异步编程学习笔记

> 面向零基础，结合本项目 `src/middleware/guardrails_middleware.py` 的真实代码整理。
> 核心问题：异步编程是什么、事件循环如何调度、`await` / `create_task` / `wait_for` 三种姿态如何取舍。

---

## 一、异步要解决的根本问题：等待时的浪费

程序里的慢操作（最典型是**网络请求**：调用大模型、访问 LangSmith、读写数据库）绝大部分时间都在"等对方回应"，CPU 本身几乎没干活。

- **同步（阻塞）**：一个执行流遇到慢操作就原地干等，等待期间什么都做不了。
- **异步（非阻塞）**：遇到慢操作时先"让出"，去处理别的就绪任务，等操作完成再回来继续。把"干等"的时间利用起来。

**餐厅比喻**（单线程 = 只有一个服务员）：

| 餐厅 | 异步世界 |
|---|---|
| 服务员 | 事件循环（单线程调度器） |
| 某桌点的菜要做 10 分钟 | 协程发起的 IO 操作（如网络请求） |
| "做菜的那 10 分钟" | 就是被"等待"的那个操作 |
| 服务员转身去照看别的桌 | 事件循环切去运行别的就绪协程 |
| 菜好了按铃 | IO 有响应，操作系统通知事件循环 |

---

## 二、三个核心语法关键字

### 1. `async def` —— 声明异步函数（协程函数）

```python
async def _add_to_dataset(self, ...):
```

调用它不会立刻执行，而是返回一个**协程对象**（一张"待办任务单"），必须交给事件循环驱动才真正运行。

### 2. `await` —— "这里要等，等的时候让别人先上"

```python
dataset = await client.read_dataset(...)
```

- 只能出现在 `async def` 内部。
- 语义："这一行是慢操作，我现在**暂停**、交出控制权；事件循环去跑别的任务；等操作完成再回到这里继续。"
- **规则：凡是需要等待的调用，前面都要加 `await`。** 忘记 `await` 只会拿到协程对象，实际代码根本没执行（新手最常见 bug）。

### 3. 事件循环（Event Loop）—— 总调度器

单线程 + 事件循环 + `await` 让车，就实现了"一个服务员同时照看多桌"的并发效果。它的运行逻辑是一个**轮转循环**：

```
反复地：
  1) 问操作系统：有哪些 IO 完成了？→ 把对应协程标记为「就绪」
  2) 依次运行每个就绪协程，让它一直执行，
     直到它自己遇到 await（需要等）再次让出控制权
  3) 回到第 1 步
```

---

## 三、关键澄清：`await` 到底在"等"什么

**「等的那个操作」= 协程自己通过 `await` 发起的那个底层 IO（网络/磁盘等）本身。**

常见误解与纠正：

- ❌ "等的是别的协程 B 执行完。"
- ✅ 一个协程何时恢复，**只取决于它自己发起的那个 IO 有没有回来**，与别的协程进度无关。协程 B 只是"等待期间被顺手调度去跑的别的任务"。

**谁在真正"等"？——是操作系统，不是事件循环傻等。** `await` 让出后：

1. IO 请求（如 TCP 数据包）交给操作系统发起；
2. 事件循环向操作系统登记："这个连接一旦有数据回来就告诉我"（底层靠 `epoll`/`select`/`kqueue` 等 IO 多路复用）；
3. 登记完事件循环立刻去跑别的就绪协程，**并没有为这个 IO 占用时间**；
4. 响应到达 → 操作系统通知 → 事件循环把该协程标记为就绪 → 下一轮调度时它从暂停那行复活。

**时间轴示例**（A、B 各自等自己的网络请求）：

```
t0  A 运行 → await(请求X) → 交给OS登记 → A 暂停让出
t1  事件循环转向 → B 运行 → await(请求Y) → 登记 → B 暂停让出
t2  无就绪协程 → 事件循环空转，问OS：X/Y 回来了吗？
t3  OS 通知：X 回来了 → A 标记就绪
t4  调度 → A 复活继续跑（此时 Y 可能还没回，B 仍在暂停，A 的恢复与 B 无关）
t5  OS 通知：Y 回来了 → B 复活
```

---

## 四、三个重要认知点

1. **异步 ≠ 多线程/多核并行**。它始终是**单线程**，只是把"等待时间"利用起来。CPU 密集计算（疯狂算数）用异步没用，那需要多进程。异步专治 **IO 等待**。
2. **协程不会自动并发**。在异步函数里连续 `await A()` 再 `await B()` 是**串行**的（A 完了才 B）。要"同时"跑，需显式用 `asyncio.gather(...)` 或 `asyncio.create_task(...)`。
3. **同步 vs 异步钩子的选择取决于"是否调外部服务"**。本项目 `ingress_guards` 只做字符串截断（纯 CPU），用同步 `before_agent`；`guardrails` 要调 LLM（网络 IO），用异步 `abefore_agent`。

---

## 五、两种异步调用姿态：`await` vs `create_task`

同一个异步函数，有两种调用方式，语义完全不同：

```python
# 姿态①：await —— 我要等它做完，拿到结果再继续
await self._add_to_dataset(...)

# 姿态②：create_task —— 丢给事件循环后台跑，我不等，立刻往下走
asyncio.create_task(self._add_to_dataset(...))
```

| 维度 | `await` | `create_task`（发射后不管） |
|---|---|---|
| 调用方是否暂停 | 是，被"钉"在此等结果 | 否，瞬间返回继续跑 |
| 被调用者位置 | 串进主路径 | 挪出主路径，后台并发 |
| 能否拿结果/接异常 | 能 | **都不能**（除非后续 await 该 task） |
| 适用场景 | 主流程依赖其结果 | 旁路观测、结果无关 |

### `create_task` 的两个代价（决定了代码写法）

`create_task` 不 `await`，等于放弃了对该任务的两样控制权：

1. **拿不到结果、接不住异常**：任务内部异常不会冒到调用方；若无人检索，会变成"未处理任务异常"告警甚至被静默吞掉。
   → **这正是 `_add_to_dataset` 内部必须自带"包全场"的 `try/except: logger.warning(...)` 的原因**——外部不接异常，它就得自己负责到底。
2. **生命周期可能"没跑完就被回收"**：若事件循环很快关闭，后台任务可能未完成即被丢弃；不持有 task 引用理论上还可能被 GC。
   → 护栏对此的态度是"丢了也无所谓"（本就是抽样写评估集），符合旁路定位。

**结论**："发射后不管的调用方式"与"被调用者自我兜底"是一对必须同时成立的设计。

## 六、超时保护：`asyncio.wait_for`

对于"**必须拿结果、又怕它无限期卡死**"的调用（如分类），用 `wait_for` 把"无限等待"变成"有期限等待"：

```python
result = await asyncio.wait_for(
    structured_llm.ainvoke(prompt, ...),
    timeout=GUARDRAILS_TIMEOUT_SECONDS,   # = 10
)
```

机制：包成后台任务开始等，同时启动倒计时，两种结局谁先到算谁：

- 10 秒内完成 → 正常返回结果；
- 10 秒到仍未完成 → **主动取消**那个任务（掐掉），并抛出 `asyncio.TimeoutError`。

放回事件循环模型：正常 `await` 是"等 OS 通知 IO 完成才复活"；`wait_for` 额外挂了个"**定时器也算一种唤醒源**"——就算 IO 通知不来，10 秒后也会被"超时异常"打断，协程绝不会永远卡住。

### 与"重试 + 主/备降级链"的咬合

`TimeoutError` 也是 `Exception` 子类，会被降级循环的 `except Exception` 精确接住（`_classify_query` 第 438 行），于是：

> **"卡住超时"被当成"这次调用失败"，与"网络报错""返回坏结果"一视同仁**，统一进入"重试 → 换备用模型 → 全失败抛 `GuardrailsClassificationError` → 上层 fail-open 放行"的流程。

执行轨迹示例（主模型每次卡死、备用模型正常）：

```
主模型 第1次 → 等满10s → TimeoutError → 重试
主模型 第2次 → 等满10s → TimeoutError → 重试
主模型 第3次 → 等满10s → TimeoutError → 试满 → 降级到备用模型
备用模型 第1次 → 3s 返回 → wait_for 立即结束 → return ✅
```

**没有 `wait_for` 会怎样**：主模型第一次卡死后，代码会在第一个 `await` 上**永远停住**，重试/降级/fail-open 全都轮不到执行，用户彻底卡死。所以 `wait_for` 是"让降级链有机会被触发"的前提。

### 一个易忽略的代价：超时是"逐次"而非"总预算"

`timeout=10` 是**每次单独调用**的封顶，最坏总耗时：

```
最坏耗时 ≈ 模型数 × 每模型尝试数 × 单次超时 = 2 × 3 × 10s ≈ 最多约 60s
```

即"重试/降级提升可靠性，但会线性拉长最坏延迟"。要收紧可：调小重试次数、减小单次 timeout，或在 `_classify_query` 外再套一层总预算 `wait_for`。无论链多长终将结束并 fail-open——护栏底线永远是"要么给出判定，要么放行用户，绝不无限期拒客"。

## 七、总收束：本项目的"等 / 不等"编排

| 场景 | 用法 | 为什么 |
|---|---|---|
| 旁路、结果不重要 | `create_task`（不 await） | 不占用户响应路径；被调用者自我吞异常 |
| 必须拿结果 | `await` | 主流程依赖它才能继续 |
| 必须拿结果、但怕卡死 | `await asyncio.wait_for(coro, timeout)` | 无限等待变有限；超时=一次失败喂给降级链 |
| 纯内存、无 IO | 同步 `def`（如 `_track_decision_metadata`） | 没有可让出的等待，异步反成累赘 |

一句话打通：**"要不要等"（await vs create_task vs 同步）→ "等但要设时限"（wait_for）→ "等失败了怎么办"（重试 → 主/备降级 → fail-open）**。这条异步与容错链路，正是 Agent 工程里"延迟 vs 可靠性"权衡的核心。

## 八、护栏中间件异步函数逐个看

把前面概念落到 `guardrails_middleware.py` 的四个真实函数上，看清"异步姿态"在一次请求里如何分工。

### 1. `abefore_agent`（异步钩子，总指挥）

用 `async def` 实现 `abefore_agent`（而非同步 `before_agent`），因为它要调 LLM。一次请求里三种异步姿态同时出现：

```python
try:
    guardrails_decision = await self._classify_query(messages)   # ① await：必须拿分类结果
except GuardrailsClassificationError:
    return {"off_topic_query": False}                            #    全失败 → fail-open 放行

if decision == "BLOCKED" or random.random() < ALLOWED_SAMPLE_RATE:
    asyncio.create_task(self._add_to_dataset(...))               # ② create_task：旁路采样，不等

off_topic_message = await self._generate_rejection_message(...)  # ③ await：要拿婉拒语文本
```

- 分类、婉拒语是主流程依赖的结果 → `await`（内部再套超时）。
- 写评估集是旁路观测 → `create_task` 发射后不管。

### 2. `_classify_query`（await + wait_for + 重试/降级）

外层遍历"主/备用模型链"、内层重试，每次调用都套 `wait_for`：

```python
for model_name, llm in self.classifier_llms:          # 降级链
    for attempt in range(GUARDRAILS_MAX_RETRIES + 1):  # 每模型试 3 次
        try:
            result = await asyncio.wait_for(            # 必须等 + 10s 封顶
                structured_llm.ainvoke(prompt, ...),
                timeout=GUARDRAILS_TIMEOUT_SECONDS,
            )
            return result                               # 任一模型成功即返回
        except Exception as e:                          # TimeoutError 也归此类
            if attempt < GUARDRAILS_MAX_RETRIES:
                continue                                # 同模型重试
            # 试满 → 进入下一轮 for，换备用模型
raise GuardrailsClassificationError(...)                # 全链失败 → 抛异常给上层 fail-open
```

要点：`wait_for` 保证每格循环最多 10s 必然推进，"卡死"被收敛为"一次普通失败"，从而让重试/降级能被触发。

### 3. `_generate_rejection_message`（await + wait_for + 降级兜底）

同样是"必须等结果"的调用，失败时降级到固定话术，不抛异常：

```python
try:
    response = await asyncio.wait_for(
        self.llm.ainvoke(prompt), timeout=GUARDRAILS_TIMEOUT_SECONDS,
    )
    return AIMessage(id=response.id, content=response.content)
except Exception as e:
    logger.error(...)                                   # 超时/报错 → 记日志
    return AIMessage(content=_FALLBACK_REJECTION_MESSAGE)  # 降级为预设婉拒语
```

### 4. `_add_to_dataset`（async with + 自我吞异常）

被 `create_task` 发射后不管，所以内部必须对自己负责到底：

```python
try:                                                    # 全包式 try，兜住一切
    async with ls.AsyncClient() as client:              # 异步客户端：进出需 await
        if _dataset_id_cache is None:                   # 模块级缓存，避免重复查询
            try:
                dataset = await client.read_dataset(...)
            except Exception:
                dataset = await client.create_dataset(...)   # 读不到则创建（get-or-create）
        await client.create_example(...)                # 写样本（IO，await）
except Exception as e:
    logger.warning(...)                                 # 任何失败仅记日志，绝不外抛
```

因为调用方不 `await` 它、接不住异常，这里的"包全场 try/except"就是它必须自备的兜底。
